## 1. Résumé exécutif

L'audit a couvert **100% des fichiers** du dépôt MonMenu sur la branche `main`. Au total, **34 bugs** ont été identifiés, répartis comme suit :

| Sévérité | Nombre | Risque principal |
|----------|--------|-----------------|
| 🔴 CRITIQUE | 3 | Authentification brisée, double confirmation silencieuse |
| 🟠 MAJEUR | 16 | Écritures silencieuses (0 lignes), mauvais niveau d'auth, missing rate-limit |
| 🟡 MINEUR | 12 | Nettoyage cosmétique, optimisations, edge cases non gérés |
| 🔵 INFO | 3 | Observations architecturales, risques latents |

**Points positifs relevés** :
- La fonction centrale `verifierAccesTenant()` est correcte et cohérente
- La validation MIME par magic bytes (3 couches) est exemplaire
- L'architecture D1 → Supabase-only pour les plans est proprement migrée
- Le wrapper `fetchAvecSession` avec refresh automatique est bien conçu
- Les fonctions lib (brevo, whatsapp, fcm) sont toutes conçues best-effort (non-bloquantes)
- Le cron est idempotent et ses 4 déclenchements séparés sont une bonne pratique
- La CSP et les headers de sécurité sont correctement configurés

**Points critiques à corriger en priorité absolue** :
1. **B-AUTH-01** : `/reset-password` → `auth.updateUser()` sans session GoTrue → HTTP 500 garanti
2. **B-ADPAY-01/.catch() sur insert PostgREST** : API invalide sur `PostgrestFilterBuilder`
3. **B-ADPAY-03** : Race condition double confirmation paiement → tenant activé deux fois

### 4.1 `src/routes/api-auth.ts`

**Lignes auditées** : ~600 lignes

#### 🔴 B-AUTH-01 — CRITIQUE : `/reset-password` → `auth.updateUser()` sans session GoTrue

**Localisation** : ligne ~535

```typescript
// CODE BUGUÉ
const supabase = createSupabaseClient(c.env) // singleton ANON partagé, PAS de session active
const { data: { user }, error: userError } = await supabase.auth.getUser(token) // OK : vérifie le token
if (userError) { clearAuthCookies(c); return c.json({ error: '...' }, 401) }

const { error } = await supabase.auth.updateUser({ password: body.password })
// ☠️ CRITIQUE : auth.updateUser() sur le singleton sans session → "Auth session missing!" → 500
```

**Impact** : La route `/reset-password` est **complètement non fonctionnelle**. Tout utilisateur tentant de réinitialiser son mot de passe via le lien reçu par email obtiendra une erreur 500. Aucune réinitialisation de mot de passe n'est possible.

**Correctif** :
```typescript
// CORRECTION : utiliser adminClient.auth.admin.updateUserById()
const adminClient = createSupabaseAdminClient(c.env)
const { data: { user }, error: userError } = await adminClient.auth.admin.getUserById(userId)
// ... vérifications ...
const { error } = await adminClient.auth.admin.updateUserById(user.id, { password: body.password })
```

Cette approche est déjà utilisée correctement dans `api-dashboard.ts` → `POST /profil/change-password`.

#### 🟠 B-AUTH-02 — MAJEUR : Rate limiting sans KV (fallback mémoire locale)

**Localisation** : fonctions login et register

```typescript
const rateLimit = await checkRateLimit(`auth_login:${ip}`, 5, 900000)
// KV_CACHE non passé → fallback Map en mémoire locale de l'isolate
// → rate limiting NON distribué : chaque isolate Workers a son propre compteur
// → un attaquant peut contourner en ciblant différentes instances
```

**Impact** : Le rate limiting sur les endpoints d'authentification est inefficace sous Cloudflare Workers avec de la charge distribuée. Un attaquant peut tenter un bruteforce depuis plusieurs IPs sur plusieurs instances.

**Correctif** : Passer `c.env.KV_CACHE` à `checkRateLimit()`.

#### 🟠 B-AUTH-04 — MAJEUR : Register → insertions sans vérification résultat

```typescript

await adminClient.from('utilisateurs_tenant').insert({...}) // idem
```

#### 🟡 B-CMD-03 — MINEUR : Race condition incrément usage promo

```typescript
c.executionCtx.waitUntil(
  adminClient.rpc('increment_promo_usage', { promo_id: promoId })
    .then(({ error }) => { if (error) { /* fallback UPDATE manuel */ }})
)
```

Si deux commandes arrivent simultanément avec le même code promo, les deux incréments s'exécutent en parallèle. Si `usage_max` est défini à 1, le code promo peut être utilisé deux fois sans erreur (la vérification `usage_actuel < usage_max` est faite AVANT l'incrément non-atomique).

**Correctif** : La fonction RPC `increment_promo_usage` doit être implémentée comme une transaction atomique avec vérification `usage_actuel < usage_max` à l'intérieur.

### 4.5 `src/routes/api-admin-paiements.ts`

#### 🔴 B-ADPAY-01 — CRITIQUE : `.catch()` invalide sur `PostgrestFilterBuilder`

```typescript
// LIGNE ~223 et ~237 (confirmation) et ~344 et ~357 (rejet)
await adminClient
  .from('notifications_restaurant')
  .insert({ ... })
  .catch(() => {}) // ☠️ PostgrestFilterBuilder ne dispose PAS de .catch() natif
                   // → TypeError: adminClient.from(...).insert(...).catch is not a function
```

**Explication technique** : `PostgrestFilterBuilder` est un objet "thenable" (possède `.then()`) mais n'implémente pas l'interface `Promise` complète. `.catch()` n'est pas garanti et peut lever `TypeError` selon la version de `@supabase/supabase-js`.

**Correctif** :
```typescript
try {
  await adminClient.from('notifications_restaurant').insert({ ... })
} catch { /* silencieux */ }
```

#### 🔴 B-ADPAY-03 — CRITIQUE : Race condition double confirmation paiement

```typescript
const { error: abError } = await adminClient.from('abonnements')
  .update({ statut: 'actif', ... })
  .eq('id', abonnement_id)
  .eq('statut', 'en_attente_confirmation') // Guard idempotence

if (abError) { return c.json({ error: '...' }, 500) }
// ☠️ Si 0 lignes affectées (déjà confirmé par une requête parallèle) :
// abError = null, data = [] → on continue et on active le tenant une seconde fois !
```

**Impact** : Deux admins qui confirment le même paiement simultanément → le tenant est activé deux fois, deux abonnements créés, date_fin calculée sur le premier abonnement mais écrasée par le second. Incohérence comptable.

**Correctif** : Vérifier que `data.length > 0` après l'UPDATE :
```typescript
const { data: abData, error: abError } = await adminClient.from('abonnements')
  .update({ statut: 'actif', ... })
  .eq('id', abonnement_id)
  .eq('statut', 'en_attente_confirmation')
  .select('id')

if (abError) return c.json({ error: '...' }, 500)
if (!abData || abData.length === 0) {
  return c.json({ error: 'Paiement déjà traité.' }, 409)
}
```

## 5. Audit détaillé — Fichiers lib

### 5.1 `src/lib/supabase.ts`

#### 🟠 B-SUP-01 — MAJEUR (structurel) : Clients mis en cache module-level

```typescript
let _client: SupabaseClient | null = null
let _adminClient: SupabaseClient | null = null

export function createSupabaseClient(env: SupabaseEnv): SupabaseClient {
  if (!_client) {
    _client = createClient(env.SUPABASE_URL, env.SUPABASE_ANON_KEY, {...})
  }
  return _client
}
```

**Problème** : Dans une isolate Workers "chaude" (non-recyclée), ce singleton persiste entre requêtes. Le commentaire interne dit "Workers sont stateless" ce qui est vrai entre requêtes sur des isolates différentes, mais **faux dans la même isolate**. En production avec du trafic, plusieurs requêtes simultanées partagent le même client Supabase.

**Risque concret** : Si un client est configuré avec un Bearer token utilisateur A, et qu'un autre appel pour l'utilisateur B arrive dans la même isolate avant que le singleton soit recyclé, le token A peut être réutilisé. Cependant, étant donné que `createSupabaseClientWithToken()` crée un nouveau client à chaque fois (non caché), ce risque est mitigé dans la pratique.

**Risque réel actuel** : Principalement le client ANON partagé (pas de token user) → risque faible mais préoccupation architecturale.

## 6. Audit détaillé — Middleware

### 6.1 `src/middleware/auth.ts`

**Analyse** : Deux middlewares bien séparés (`authMiddleware` pour les routes tenant, `authMiddlewarePlatform` pour les routes plateforme). Extraction token cookie ou header correcte.

#### 🟠 B-MID-01 — MAJEUR : Lookup `utilisateurs_tenant` via client RLS-scopé

```typescript
export const authMiddleware = async (c, next) => {
  // ...
  const supabaseToken = createSupabaseClientWithToken(c.env, token) // RLS actif
  const { data: utData, error: utError } = await supabaseToken
    .from('utilisateurs_tenant')
    .select('tenant_id, tenants!inner(id, slug, statut, deleted_at)')
    .eq('auth_user_id', user.id)
    .is('tenants.deleted_at', null)
    .neq('tenants.statut', 'suspendu')
    .single()
```

**Problème** : Ce middleware utilise un client avec le token JWT de l'utilisateur (RLS actif). Si la policy RLS sur `utilisateurs_tenant` est trop restrictive ou mal configurée, le middleware peut retourner 403 pour un utilisateur légitime.

**Impact en pratique** : Si les policies RLS sont correctement configurées pour permettre à un utilisateur de lire sa propre entrée `utilisateurs_tenant`, ce bug n'est pas déclenché. Mais c'est une fragilité architecturale.

**Correctif recommandé** : Utiliser `createSupabaseAdminClient(c.env)` pour le lookup `utilisateurs_tenant`, puis vérifier manuellement que `auth_user_id` correspond à l'utilisateur authentifié.
