## Audit — src/routes/api-blog.ts

### 🔴 BUG-01 (CRITIQUE) — Middleware ADMIN_EMAILS déclaré APRÈS les routes qu'il protège

**Fichier :** `src/routes/api-blog.ts`  
**Lignes concernées :** Routes POST (ligne ~50), PATCH (ligne ~83), DELETE (ligne ~122) vs Middleware (ligne 143)

**Description du bug :**

Dans Hono (comme dans Express), les middlewares et routes sont appliqués **dans l'ordre de déclaration**. Le fichier est structuré ainsi :

```
Ligne  12 : blogRouter.use('/admin/*', authMiddlewarePlatform)  ← vérifie JWT ✅
Ligne  50 : blogRouter.post('/admin', ...)                       ← ROUTE
Ligne  83 : blogRouter.patch('/admin/:id', ...)                  ← ROUTE
Ligne 122 : blogRouter.delete('/admin/:id', ...)                 ← ROUTE
Ligne 143 : blogRouter.use('/admin/*', async (c, next) => {      ← vérif ADMIN_EMAILS ❌
              // ce middleware n'est JAMAIS exécuté pour les routes ci-dessus
            })
```

Un middleware enregistré après une route ne s'applique pas à cette route. La vérification de la liste blanche d'emails (`ADMIN_EMAILS`) ne s'exécute **jamais** sur `POST /admin`, `PATCH /admin/:id`, ou `DELETE /admin/:id`.

**Scénario de déclenchement :**
1. Un restaurateur lambda dispose d'un compte Supabase valide (créé via `/api/v1/auth/register`).
2. Il extrait son `access_token` depuis le cookie `sb-access-token`.
3. Il appelle `DELETE /api/v1/blog/admin/<uuid-article>` avec `Authorization: Bearer <son_token>`.
4. L'article est supprimé — aucune vérification d'email n'a eu lieu.

**Impact :** Tout utilisateur Supabase authentifié peut créer, modifier ou supprimer n'importe quel article du blog public MonMenu.

**Sévérité :** 🔴 Critique — faille de sécurité : modification de contenu public par n'importe quel abonné.

**Correctif proposé :**

Déplacer le second middleware AVANT les routes, dans l'ordre correct :

```typescript
// api-blog.ts — ordre CORRIGÉ

blogRouter.use('/admin/*', authMiddlewarePlatform)

// Second middleware ADMIN_EMAILS — doit être déclaré AVANT les routes
blogRouter.use('/admin/*', async (c, next) => {
  const auth = c.get('auth') as any
  const adminEmails = (c.env.ADMIN_EMAILS ?? '').split(',').map((e: string) => e.trim()).filter(Boolean)
  if (adminEmails.length === 0) {
    return c.json({ error: 'Administration blog non configurée (ADMIN_EMAILS manquant).' }, 503)
  }
  const supabase = (await import('../lib/supabase')).createSupabaseClient(c.env)
  const { data: { user } } = await supabase.auth.getUser(auth.token)
  if (!user?.email || !adminEmails.includes(user.email)) {
    return c.json({ error: 'Accès réservé aux administrateurs de la plateforme.' }, 403)
  }
  return next()
})

// Routes APRÈS les middlewares
blogRouter.post('/admin', async (c) => { ... })
blogRouter.patch('/admin/:id', async (c) => { ... })
blogRouter.delete('/admin/:id', async (c) => { ... })
```

**Fichiers additionnels impactés :** `src/types/database.ts` — `ADMIN_EMAILS` n'est pas déclaré dans le type `Env` (voir BUG-15).

### 🟠 BUG-02 (Majeure) — DELETE /admin/:id sans validation UUID et sans vérification de lignes affectées

**Fichier :** `src/routes/api-blog.ts`, lignes 122-130

**Description :**

La route DELETE du blog ne valide pas que `id` est un UUID valide (contrairement à `PATCH /admin/:id` qui valide via `UUID_BLOG_REGEX`). Elle ne vérifie pas non plus les lignes affectées :

```typescript
const { error } = await adminClient.from('articles').delete().eq('id', id)
if (error) {
  return c.json({ error: "Impossible de supprimer l'article." }, 500)
}
return c.json({ success: true })  // success:true même si 0 lignes supprimées
```

**Scénario :** `DELETE /api/v1/blog/admin/id-inexistant` → répond `{ success: true }`.

**Correctif proposé :**
```typescript
blogRouter.delete('/admin/:id', async (c) => {
  const id = c.req.param('id')
  const UUID_REGEX = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i
  if (!UUID_REGEX.test(id)) {
    return c.json({ error: 'Format id invalide (UUID v4 attendu).' }, 422)
  }
  const adminClient = createSupabaseAdminClient(c.env)
  const { data: deletedRows, error } = await adminClient
    .from('articles').delete().eq('id', id).select('id')
  if (error) return c.json({ error: "Impossible de supprimer l'article." }, 500)
  if (!deletedRows || deletedRows.length === 0) return c.json({ error: 'Article introuvable.' }, 404)
  return c.json({ success: true })
})
```

## Audit — src/routes/api-cron.ts

### 🟠 BUG-06 (Majeure) — bloquerPaiementsExpires() : filtre .eq('statut', 'essai') trop restrictif

**Fichier :** `src/routes/api-cron.ts`, lignes ~510-525

**Description :**

Dans `bloquerPaiementsExpires()`, quand une fenêtre de grâce 72h expire, le code tente de passer le tenant en `inactif` :

```typescript
await adminClient
  .from('tenants')
  .update({
    statut: 'inactif',
    paiement_en_attente_depuis: null,
    updated_at: nowIso
  })
  .eq('id', tenant.id)
  .eq('statut', 'essai')  // ← filtre sur 'essai' UNIQUEMENT
```

Si le tenant a le statut `'en_attente_paiement_initial'` (nouveau restaurant ayant soumis un paiement avant d'être activé), le filtre `.eq('statut', 'essai')` ne matche pas → UPDATE touche 0 lignes sans erreur → `paiement_en_attente_depuis` reste non null → la notification d'attente s'affiche indéfiniment au tenant.

**Scénario de déclenchement :**
1. Nouveau restaurant → statut `'en_attente_paiement_initial'`.
2. Soumet preuve → abonnement `'en_attente_confirmation'`.
3. Admin ne confirme pas dans les 72h.
4. Cron expire l'abonnement ✅.
5. Cron **ne** réinitialise PAS `paiement_en_attente_depuis` (filtre 'essai' ne matche pas).
6. Notification "paiement en attente" reste affichée, même après expiration.

**Correctif proposé :**

Élargir le filtre ou ne pas filtrer sur statut pour cette mise à jour :

```typescript
// Option 1 : filtre élargi
.in('statut', ['essai', 'en_attente_paiement_initial', 'inactif'])

// Option 2 : ne pas filtrer (UPDATE idempotent)
.eq('id', tenant.id)
// Pas de filtre sur statut — on veut juste effacer paiement_en_attente_depuis
```

### 🟠 BUG-13 (Majeure) — POST /confirmer : date_fin calculée avec setMonth() → débordement en fin de mois

**Fichier :** `src/routes/api-admin-paiements.ts`, lignes ~185-195

**Description :**

```typescript
const fin = new Date()
fin.setMonth(fin.getMonth() + 1)
dateFin = fin.toISOString()
```

`Date.setMonth()` en JavaScript gère les débordements : si la date courante est le **31 janvier** et qu'on ajoute 1 mois, `fin` devient le **3 mars** (31 février n'existe pas → JavaScript avance automatiquement au 3 mars). Un abonnement confirmé le 31 janvier se termine le 3 mars au lieu du 28/29 février.

**Mois affectés :** 31 jan, 31 mars, 31 mai, 31 juil, 31 août, 31 oct, 31 déc.

**Impact :** Le tenant bénéficie de 2-3 jours d'abonnement supplémentaires sans payer.

**Correctif proposé :**
```typescript
// Ajouter exactement 1 mois sans débordement
const fin = new Date()
const jourDuMois = fin.getDate()
fin.setDate(1)  // Aller au 1er du mois courant
fin.setMonth(fin.getMonth() + 1)  // Aller au 1er du mois suivant
// Reposer au bon jour (min entre jour original et dernier jour du mois suivant)
const dernierJourMoisSuivant = new Date(fin.getFullYear(), fin.getMonth() + 1, 0).getDate()
fin.setDate(Math.min(jourDuMois, dernierJourMoisSuivant))
dateFin = fin.toISOString()
```

## Audit — src/lib/supabase.ts

### 🔴 BUG-14 (CRITIQUE) — Client Supabase singleton mis en cache au niveau module

**Fichier :** `src/lib/supabase.ts`, lignes 12-36

**Description :**

```typescript
let _client: SupabaseClient | null = null  // ← singleton partagé

export function createSupabaseClient(env: SupabaseEnv): SupabaseClient {
  if (!_client) {
    _client = createClient(env.SUPABASE_URL, env.SUPABASE_ANON_KEY, {
      auth: { autoRefreshToken: false, persistSession: false }
    })
  }
  return _client  // ← même instance pour TOUTES les requêtes de l'isolate
}
```

Sur Cloudflare Workers, une isolate peut traiter **plusieurs requêtes concurrentes** pendant sa durée de vie (warm start). Le singleton `_client` est partagé entre ces requêtes.

Ce bug était déjà identifié (pattern #4 de l'audit précédent) et est toujours présent. La route `POST /profil/change-password` crée explicitement un `createClient(...)` frais pour se protéger — indiquant que les développeurs ont conscience du problème mais ne l'ont pas résolu à la racine.

**Risque :** Si une requête future appelle `setSession()` sur le singleton (erreur de code), elle posera la session pour toutes les requêtes concurrentes utilisant le même client.

**Constat actuel :** En l'état, `persistSession: false` et l'absence de `setSession()` limitent le risque. Mais l'architecture est fragile.

**Correctif complet :** Créer un client par requête (impact performance minimal — Supabase JS est léger) :
```typescript
// Supprimer le cache module-level
export function createSupabaseClient(env: SupabaseEnv): SupabaseClient {
  return createClient(env.SUPABASE_URL, env.SUPABASE_ANON_KEY, {
    auth: { autoRefreshToken: false, persistSession: false }
  })
}
```

**Fichier :** `src/middleware/auth.ts`, lignes 69-80

### 🟡 BUG-17 (Mineure) — Cache KV du null retournant une string truthy

**Fichier :** `src/index.tsx`, lignes 97-105

**Description :**

```typescript
// Écriture en cache du null
try { await env.KV_CACHE.put(cacheKey, 'null', { expirationTtl: 10 }) } catch {}
return null

// Lecture depuis cache
const cached = await env.KV_CACHE.get(cacheKey, 'json')
if (cached !== null) return cached as TenantBoutique | null
```

`KV.get(key, 'json')` sur la valeur `'null'` retourne `null` (JSON.parse de la string "null" = null en JavaScript). Donc en réalité ce comportement est correct — `JSON.parse('null') === null`, et `cached !== null` sera `false`, le cache manquera. 

**Cependant**, le `'null'` string stocké en cache représente 4 bytes pour décoder en null. Les 10 secondes de cache anti-DoS fonctionnent mais avec une lisibilité trompeuse. Aucun bug réel ici — juste un code difficile à lire.

## Améliorations Recommandées

Ces points ne sont pas des bugs à proprement parler, mais des faiblesses de conception :

### A-01 — Finaliser la migration CSP vers nonces stricts

Toutes les pages devraient passer le nonce de `setSecurityHeaders(c)` à leurs templates `<script nonce="...">`, puis supprimer `'unsafe-inline'`. En l'état, la CSP script-src ne protège rien.

### A-02 — Mutualiser la logique d'authentification dans un helper central

Les fonctions `verifyAuth`, `verifyAuthOnboarding`, `verifyAuthPaiement`, `verifyRestaurantAuth` ont des structures quasi-identiques dans 4 fichiers différents. Un helper central dans `src/lib/` réduirait la duplication et le risque de divergence.

### A-03 — Ajouter KV_CACHE dans wrangler.jsonc

KV est essentiel pour le rate limiting distribué et le cache boutique. Ajouter le binding en production.

### A-04 — Unifier validerMimeImage entre lib/paiement.ts et lib/validation.ts

`lib/paiement.ts` possède encore sa propre version async de `validerMimeImage` (différente de `validerMimeImageUnifie()` dans `lib/validation.ts`). La migration complète (documentée comme "tâche future") devrait être réalisée.

### A-05 — Statuts de tenant acceptés pour commandes publiques : constante partagée

La liste `['actif', 'essai', 'en_attente_paiement_initial']` est définie en dur dans `api-commandes.ts` ET `api-tenants.ts`. Un changement futur doit être répercuté dans les deux. Envisager une constante partagée dans `lib/constants.ts`.

### A-06 — CSRF protection sur POST /api/v1/contact

La route contact n'a pas de vérification `X-Requested-With`. Rate limiting IP présent, mais un CSRF depuis un autre site est possible. Cohérence avec les autres routes POST du projet.

### A-07 — POST /suppressions/:tenant_id/executer sans rate limiting

Cette route destructive (suppression définitive d'un compte) n'a pas de rate limiting. Un secret admin compromis pourrait déclencher des suppressions en masse. Ajouter `checkRateLimit`.

### A-08 — Duplication PATCH /commandes/:id/statut (commentaire B-CMD-02)

Maintenir deux copies identiques de la même logique est fragile. Envisager un helper commun appelé par les deux routes (dashboard et mobile).

### A-09 — Logging explicite des UPDATEs à 0 lignes dans les crons

Ajouter `.select('id')` sur tous les UPDATEs des crons et logger explicitement les cas où 0 lignes sont affectées pour faciliter le débogage.
